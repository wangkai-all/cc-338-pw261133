# 删除依据台账（Catalog Withdrawal Ledger）

一个**从零实现、零第三方依赖**的本地系统，用于回答一个具体问题：

> 目录里的某条资料不见了，究竟是**真实撤回**、**暂时不可见**，还是**我们没抓全**？

系统由四个进程内组件构成，一条命令启动：

| 组件 | 端口 | 作用 |
|---|---|---|
| 台账后台 + API | 8080 | 判定、台账、补扫、投递、看板 |
| 本地发布站点 | 8090 | 可切换地区与故障的模拟站点 |
| 下游目录服务 | 8091 | 接收下架/发布事件，维护对外内容 |
| SQLite ×2 | — | `data/ledger.db` 台账 · `data/downstream.db` 下游 |

```bash
python3 run.py --seed     # 启动全部服务并写入演示场景
python3 run.py            # 只启动，不写演示数据
python3 run.py --check    # 离线策略自测（30 项，不需要浏览器）
```

打开 <http://127.0.0.1:8080/>。

---

## 1. 问题拆解

每天全量扫描目录，站点会：

* 按地区**临时屏蔽**部分页面（403 / 451 / 200 错误提示页）；
* 返回**带错误提示的正常状态码**（200 的“服务不可用”页）；
* **截断**目录或正文；
* 因缓存/路由返回**错误地区**的内容；
* 偶发 5xx、超时。

因此“这次没看到”有四种完全不同的含义：

| 观测 | 含义 | 正确反应 |
|---|---|---|
| 目录完整、正文墓碑页 / 404 | 真实撤回（强证据） | 累积到门槛后撤回 |
| 地区 403/451、200 错误页、正文受限 | 暂时不可见 | **待复核**，不删 |
| 列表条数少于声明总数、正文缺结束标记 | 抓取不全 | **扫描作废**，补扫 |
| 响应地区 ≠ 请求地区 | 缓存/路由错误 | **扫描作废**，补扫 |

核心设计原则：**删除是一个需要多份证据的结论，而不是一次读数的默认值。**

---

## 2. 判定策略

### 2.1 证据门槛

一次“完整观测”必须同时满足：

1. 目录扫描成功，且两个目录边界标记齐全；
2. 声明总数存在，实际收集数等于声明总数（**截断会在这里暴露**）；
3. 响应头地区与请求地区一致；
4. 该地区目录未被整体屏蔽；
5. 条目未出现，且正文探测为墓碑页或干净 404。

自动撤回需要**同时**满足（默认值，可用环境变量调整）：

| 门槛 | 默认 | 含义 |
|---|---|---|
| 完整观测次数 | ≥ 3 | 目录被屏蔽/截断的扫描不计入 |
| 覆盖地区 | ≥ 2 | 单一地区盲区不算撤回 |
| 扫描批次 | ≥ 2 | 一次多地区扫描只算一个时间点 |
| 连续无可见 | 必须 | 最近一次完整扫描若仍可见，立即恢复 |
| 目录规模比 | ≥ 60% | 目录整体骤减视为发布方/采集故障，抬高门槛 |

证据聚合以**批次**为单位，并只统计**最近一次可见之后的连续无可见批次**（尾部连胜）。历史上的可见记录不会否决当前证据，但尾段中任何一次可见都会打断连胜。

### 2.2 歧义不计入证据

以下情况会让本次批次成为“歧义批次”，**不产生删除证据**，且会把条目推进待复核：

* 地区目录 403 / 451 / 200 错误页；
* 正文 451、200 错误页、截断（缺结束标记）、内容过短；
* 目录条数与声明总数不一致；
* 响应地区与请求地区不一致；
* 分页重复（疑似缓存）。

### 2.3 撤回通知

* 只接受**来源明确**的通知：`rights-office`、`legal-notice`、`publisher-notice-board`、`publisher-api`。
* 通知按 `notice_id` 幂等；payload 哈希留档。
* 通知**先于**正文状态到达、正文仍可读时：条目保持撤回，并标记“需人工关注”，**不自动重新发布**。
* 通知**晚于**正文消失到达：同样直接撤回，无需等待扫描门槛。

### 2.4 粘性与人工恢复

* 自动撤回不是“可被下一次扫描翻转”的普通状态。撤回后即使重新看到条目：
  * 台账保持 `retracted`，标记需人工关注；
  * 下游收到的是**永久**下架（`permanently_restricted=true`），扫描触发的发布事件被显式拒绝。
* 只有**人工恢复**（必须填写原因，写入审计）才能重新发布。

下游区分两种“撤下”，避免把临时不可见变成永久删除：

| 台账状态 | 下游 | 能否被后续扫描恢复 |
|---|---|---|
| `quarantined`（暂时不可见/歧义） | withheld，`permanently_restricted=false` | 能：完整扫描可见后自动重新发布 |
| `retracted`（真实撤回） | withheld，`permanently_restricted=true` | 不能：只接受带 `allow_restore` 的人工恢复 |

### 2.5 状态机

```
active ──完整扫描无歧义且未达门槛──▶ quarantined ──证据达门槛──▶ retracted
  │            │                        │                        │
  │            └──完整扫描可见──────────┘                        │
  │                                                              │
  └──来源通知────────────────────────────────────────────────────▶ retracted
                                                                 │
retracted ──人工恢复（填写原因+审计）─────────────────────────────▶ active
```

`quarantined` 在台账中**不等于删除**：条目保留正文快照与全部观测，下游可先行撤下以降低风险，但不会产生永久删除结论。

## 3. 成本与误删风险

| 项 | 说明 |
|---|---|
| 扫描成本 | 每地区每批次 1 次目录分页请求 ×页数；正文探测按预算抽样（默认每地区 24 次，其中 1/3 轮换覆盖存量） |
| 判定成本 | 纯本地 SQLite，无网络调用；每次判定保存当时证据快照 |
| 通知成本 | 单条通知一次写入 + 一次下游事件 |
| 误删风险 | 若站点对所有地区**长期**屏蔽同一条目，且正文也返回墓碑页，会被判为撤回。缓解：正文墓碑页是强信号；保留快照与全部观测；人工恢复成本低且有审计 |
| 误留风险 | 地区屏蔽不计入证据，可能延迟撤回；这是有意的保守取舍 |
| 下游一致性 | 发件箱 + 序号 + 幂等键；乱序/重放被下游拒绝；临时撤下与永久撤回分开记录 |

策略参数（环境变量）：

```bash
LEDGER_MIN_SCANS=3              # 完整观测次数
LEDGER_MIN_REGIONS=2            # 覆盖地区
LEDGER_MIN_SCAN_BATCHES=2       # 扫描批次
LEDGER_ANOMALY_EXTRA_SCANS=2    # 异常时的附加观测要求
LEDGER_BODY_BUDGET=24           # 每地区每批正文探测预算
LEDGER_AUTO_SCAN_INTERVAL=86400 # 自动扫描周期（秒，0 关闭）
```

## 4. 必须成立的三个不变量

1. **一次空结果绝不清库。** 单次扫描消失 → 最多 `quarantined`，且必须有正文探测支持。
2. **通知与正文的时序无关紧要。** 通知先到、正文后到；正文先消失、通知后到；重复通知——结论一致。
3. **扫描失败、地区切换不能“复活”已撤回资料。** 撤回结果粘性；下游拒绝无 `allow_restore` 的发布事件；陈旧序号事件与内容 `update` 都无权解除撤下。

这三条都有离线自测覆盖（`run.py --check`，30 项）。

## 5. 可查性

后台每个页面都对应一个操作问题：

* **总览** —— 现在有多少待复核/已撤回，哪个地区扫描异常，门槛是多少。
* **资料与依据** —— 每条的当前状态、门槛进度、最近原因。
* **证据工作台** —— 逐条查看：扫了什么、每批结论、判定历史、通知、正文快照、下游当前内容、补扫与投递记录、成本与误删提示。
* **补扫任务** —— 失败扫描自动入队，可手动补扫正文/地区。
* **下游投递** —— 发件箱状态、投递失败、下游当前内容。
* **故障演练台** —— 直接切换地区/故障并触发场景，回到证据工作台看结论。

## 6. 代码结构

```
run.py                 一键启动 / 自测入口
ledger/
  config.py            配置与策略参数
  db.py                SQLite schema（台账 + 下游）
  collector.py         目录/正文抓取、HTML 解释、完整性判定
  evidence.py          证据聚合与判定（纯函数，可单测）
  service.py           扫描编排、状态机、通知、任务、发件箱
  downstream.py        下游目录服务（幂等 + 序号）
  site.py              本地发布站点（地区 + 故障注入）
  app.py               HTTP API + 静态看板 + 后台调度
  seed.py              演示数据
web/                   看板（原生 HTML/CSS/JS）
tests/                 离线自测（30 项：22 个端到端场景 + 8 个纯函数单元）
docs/POLICY.md         判定策略与失败模式详述
```

## 7. 已知边界

* 本地演示使用固定站点的 HTML 契约（边界标记、`data-total`）。接入真实站点时需要替换 `collector.py` 的解析器，并保留“完整性判定”的语义。
* 没有做多进程队列；扫描串行、任务由单一后台线程执行，适合单机演示与中小规模目录。
* 正文抓取是抽样预算，不是每批全量；这与“删除证据来自目录完整扫描”的设计一致。
* 令牌为演示用明文；生产应通过环境变量注入并置于反向代理之后。
